# The hub feed: new arXiv papers for all projects (plan, 2026-11-13)

Status: plan; nothing built. Part of `2026-11-13-main-hub.md` (part 3, shared feed). Builds on the feed engine (slice 4c, decision 118, 119; IDEA-58), layers (IDEA-50) and the main hub server.

## 1. What exists

- `services/feed.py`: `feed_run` fetches the arXiv listing of the configured categories over a window, writes `feed.fetched` and `feed.ranked` in one batch, ranks the new entries against the project's reference works by embedding similarity (max cosine, the SPECTER2 scorer of decision 116, offline), shows the top share plus a seeded exploration draw, and records the nearest reference per shown entry. `react` and `send` (to the inbox) are human acts; `add` sends and looks the paper up.
- The fetch is cached once per category set and window in `<root>/.feed-cache/arxiv/<sha of sorted categories>/<from>_<to>/`; every page is also put into the project's blobs. `feed_run_all` runs each project's feed with one shared fetch.
- Reference works today: the seed core works (`forward_core_sources`), optionally with the included works (`core+included`).
- The per-project hub has a Daily updates page (`/p/<slug>/feed/`) with react and add buttons; nothing has been fetched on the pilot (no feed events).
- No timer: decision 63 puts scheduling outside the platform.

## 2. Rulings (researcher, 2026-11-13)

| Choice | Ruling |
|---|---|
| Where | A hub page at `/feed/`, not a project page. One arXiv pull, compared with each project; a tab per project. The per-project Daily updates product is removed from the project hubs, which link to the hub page. |
| References | The project's **core layer**: works whose current layer is `core` (the researcher's move, else the final row of the layer miner). For `agentic-science` about 95 works. Recorded with each ranking (count and hash), as now. |
| Trigger | The main hub server runs the feed once a day while it is up, as the system actor (a timer thread, one run at a time). A run is only due once per `interval_days`; a hub started after days off fetches from the last complete fetch minus the overlap, so nothing is missed. Also `factory feed run --all` for an external cron. |
| Cache | The shared fetch cache is kept for 24 hours (older directories are pruned at each run; the pages are also in each project's blobs, so nothing is lost). |
| Refetch | A button on the hub page runs the feed again ignoring the cache (a human act; one run at a time; recorded as a fetch with the cache bypassed). |
| Reactions | Per project (ruled earlier): a reaction, add or send writes to the events of the project of the tab it was made in. |

## 3. Parts

1. **Layer references.** A new `FeedReferences` value `core-layer` (default for new configurations): the reference ids are `work_layers.layers_of(project)` entries with layer `core`. The enum widens; stored `feed.configured` events stay valid. Held-out seeds stay excluded as today (R-20, R-F4). A project with no core layer refuses the run (`no-reference`), as now.
2. **Cache policy.** `feed_run` and `feed_run_all` take `bypass_cache` (skip reading the cache, still write the fresh result) and the cache keeps 24 hours (`prune_cache(root, max_age)`). The recorded fetch states whether the cache was used.
3. **Feed runner in the hub.** A `FeedRunner` in `site_server` (like `ResumeRunner`): `start(refetch)` runs `feed_run_all` in a daemon thread, one at a time, keeps the outcome for the page; a timer thread calls it when due (checked every 30 minutes) and at start. No new event type: runs write the existing `feed.fetched` and `feed.ranked` as the system actor.
4. **Hub feed page.** `/feed/` built from every project's events (a tab per project; each entry with title, authors, score, nearest core work, abstract, links; React (like/dislike), Add to inbox), a status line per project (last fetch, window, references used, entries held), the Fetch now and Refetch (no cache) buttons, and the last run's outcome. The acts post to `/p/<slug>/api/feed/react` and `/add`; two new hub acts `POST /api/feed/run` and `POST /api/feed/refetch` (token, loopback, one at a time).
5. **Configuration.** The categories are set per project by a human act (`factory feed configure`, later the setup form). A project without a configuration is listed on the page as "not configured".
6. **Decision entry.** A hub timer is a scheduler inside the hub server, outside the platform core: a proposed decision (extending decision 63) says so: the timer calls the same service the CLI calls, writes the same events as the system actor, and is off when the server is not running.

## 5. Risks

- **First live run.** The engine has never fetched on real data; expect defects (arXiv throttle, entry parsing, the embedder's first load). The first run is a dry run, then a real one with one category.
- **The embedder** (SPECTER2, offline weights) loads on the first ranking; it must not block the hub: the runner thread holds it, requests do not.
- **Timer and writes.** A run writes events while the hub rebuilds pages; the feed lock and the index lock already serialise this per project; a test runs both.
- **Held-out seeds** must never appear on the page; the engine's rule is kept and tested on the new references.
