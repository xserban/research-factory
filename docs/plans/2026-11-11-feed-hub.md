# Plan: the feed in the hub — daily updates, one-click add, a work queue and "Process now"

Date: 2026-11-11 · Status: accepted 2026-11-11 by the researcher with the recommended rulings (decision 118, provisional); building on branch `plan-feed-hub` · Builds on: `plan-feed` (slice 4c v1, decision 117), the site hub (plan 2026-11-10-site-hub, `factory site serve`) · Origin: researcher, 2026-11-11 ("the hub should slowly become like a web server where interactions are recorded and then it can call the factory"; "the idea of having a queue is very good")

## Goal

From the hub, per project, the researcher scrolls the day's feed, reacts, ticks papers and adds them to the project in one click. The added papers enter a visible **work queue**. A **Process now** button runs the agent steps (screening, then full-text and extraction steps) on what is queued, through the factory's MCP tools in a headless Claude run. Every interaction is recorded as an event. The platform still holds no keys and no model SDK.

## Direction (researcher, 2026-11-11)

The hub grows from a read-only site into a local web application. A person's interactions there are recorded as their events, and the hub calls the factory's services for them. It is the same act as the CLI through another channel. Deterministic steps run at once. Judgement steps run in Claude through MCP. Authentication and several users come later (slice 5 identity and roles).

## Rulings needing a decision (recommended options)

1. **The hub server accepts writes [confirm].** The server stays bound to loopback. It adds `POST` endpoints, one per allow-listed human act (v1: `feed react`, `feed add`, `queue process`). Each request carries a per-server-start token embedded in the page (CSRF guard), and the Host check stays. The actor is the local human principal, as for the CLI. Writes go through the same services and access rows as the CLI commands (`HUMAN_CONFIRM` for react and add). Every other method and path is still refused. This lifts the read-only invariant of `site_server.py` for these acts only.
2. **One-click add [confirm].** "Add to project" records `feed.sent` and the inbox item (unchanged), then at once runs the `supplied` lookup for that item (`inbox.resolve_links`, gated by `supplied_links`). The paper is then in the corpus and queued for screening. The inbox stays internal; the hub never shows it as a separate step. A lookup that fails leaves the item open, and the queue shows it as `lookup failed` with a retry.
3. **The work queue is computed, not stored [confirm].** It lists, per project, every added paper and the stage it has reached: added → in corpus → screened (title/abstract) → full text → converted → extracted, or stopped (excluded, not found, no document). Each stage comes from existing events. The queue holds nothing of its own, so it can never disagree with the log. It also shows other pending work by kind (screening units, extraction units) from the existing task and lease tables.
4. **Process now launches Claude Code as an outside process [confirm].** The button starts a recorded **run** (`runner.started` / `runner.finished`, system events: the project, the stage, the model, the allowed tools, the prompt blob hash, the log blob, the exit status, the counts before and after). The run executes `claude -p <prompt> --model <model> --strict-mcp-config --mcp-config <factory MCP> --allowedTools <stage tools>`, the pattern of the pilot's `screeners/run_pass.sh`. The platform does not call a model: it starts a separate program the researcher installed, with the researcher's own subscription. Every judgement is still written through MCP with the agent's provenance. The prompts are the existing skills (`rf-screen`, the extraction and miner skills), versioned in `plugin/`. There are limits: one run per project at a time, a declared model per stage (Haiku for screening, as in the pilot rulings), and a declared cap on units per run. A run never records a human act.
5. **Platform steps run by themselves [confirm].** After an add, the hub runs the deterministic steps when they become possible: the lookup (ruling 2), the full-text fetch for papers promoted at title/abstract, and the conversion. No button is needed. These are the existing services, recorded as today.

## Rigour

- Added papers are still screened under the protocol. Process now runs the same skills and passes as a manual session, with calibration and audit unchanged. Nothing added skips screening.
- A runner is never a human. A run records what it was allowed to do and what it did, so its work can be traced and its cost counted (ledger, slice 5).
- The write endpoints accept only acts the CLI already offers to a human. Adding an act to the hub means adding it to the allow-list and to its access row.
- Held-out handling is unchanged. The prompts are the existing skills, and the agent views stay the agent views.

## Open questions

1. Should the hub process automatically on a schedule as well (nightly), or only on the button?
2. Where does the runner's log live: the project's blobs (recorded) or a log folder? Recommended: blobs, with the live tail as a file.
3. Authentication beyond loopback (a hosted hub for a lab) belongs to slice 5 and is out of scope here.
