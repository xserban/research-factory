# Plan: the project site (hub) — every product of the factory in one place

Date: 2026-11-10 · Status: steps 1 to 6 built 2026-11-10 (mypy and ruff only; no tests, testing is paused); validation by the researcher pending · Origin: pilot `agentic-science`

## Problem

During the pilot, products were built as scripts in the pilot folder (`explorer.py`, `results_report.py`,
`synth.py`, `agreement_v2.py`, conversion and taxonomy reports), next to the platform's own
dashboard and exports. Consequences: some products exist only as scripts, they are not linked from one
place, they are built by hand, and a new project would not get them.

## Principles

1. **Everything the factory produces for a person to read is a product** of the project and is reachable
   from one hub page: dashboard, explorer, results, PRISMA and methods, search report, conversion
   validation, taxonomy, miners and agreement, the lineage and chronology, the wiki (vault) and the
   synthesis pages.
2. **Products are rebuildable projections of the events** (and the stored blobs). They live in the
   project folder (`projects/<slug>/site/<product>/`), never only in a script and never edited by hand.
3. **Generic code lives in `platform/src/factory/`** (services, CLI, MCP); **project-specific data**
   (taxonomy, tranches, not-acquired lists) lives in the project as versioned objects (IDEA-50), not in
   scripts; **operational runners** (headless screener and miner sessions) become `factory mine run`
   (IDEA-51). The pilot folder is then only the data root and the researcher's notes.
4. **The platform never calls a model.** A product that needs a model's judgement (a synthesis page)
   is a **document product**: Claude writes it in a session, the platform records it as an event with
   provenance (model, skill, input digest) and runs the mechanical checks (cited works exist, quotes
   verbatim, numbers from computed statistics); the hub renders the stored, checked page and flags it
   as model-written. Rebuilding the hub never regenerates it; a changed input marks it stale.
5. **Automatic:** `factory site build` builds every stale product; `factory site serve` serves the hub
   and the live dashboard, and rebuilds stale products in the background; the dashboard has a
   "Products" tab showing each product, when it was built, from which event, and whether it is stale.
   A new project gets all of it with no extra work.

## Design

- `factory/site/`: `Product` (id, title, group, description, `inputs` = the event types and blobs it
  reads, `build(project, out_dir) -> BuildResult`), a registry, a fingerprint (last relevant event id +
  parameters), a manifest `site/manifest.json` (a cache, never an event; rebuildable), and `hub.py`
  which renders `site/index.html` from the manifest.
- Product groups on the hub: Overview (dashboard, PRISMA, methods), Corpus (explorer, chronology,
  lineage, wiki vault), Evidence (results, miners and agreement, taxonomy, synthesis), Quality
  (conversion validation, full-text coverage, audits, limitations), Process (protocol, decisions, log).
- Document products: a recorded `document.page` kind (or the existing draft and interpretation
  machinery where it fits) with kinds `synthesis`, `summary`; the check report is stored with the page.
- CLI: `factory site build [--only ID] [--force]`, `site status`, `site serve [--port]`. MCP: read-only
  `site_status`. Services hold the logic; CLI and MCP only parse and format.

## Steps (each ends with a validation by the researcher)

1. Skeleton: registry, fingerprint, manifest, hub page, CLI `site build/status`; first products wrap what
   exists (dashboard static export, PRISMA, bibliography). mypy and ruff only (testing paused).
2. Port the explorer (list, timeline, chronology, lineage, graph, detail panel, structured summary) and the
   Obsidian vault as products, reading through the project index.
3. Port results, miners and agreement (the fairer measure), taxonomy and the synthesis checker.
4. Document products: record synthesis pages as stored, checked, model-written pages; render in the hub.
5. Port conversion validation, coverage and missing-works reports; project data (taxonomy, not-acquired)
   into the project as versioned objects.
6. `site serve` with background rebuild of stale products; "Products" tab in the dashboard; retire the pilot
   scripts (leave a pointer).
