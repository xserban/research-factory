# The main hub: one server for all projects (plan, 2026-11-13)

Status: plan; nothing built. Direction (researcher, 2026-11-13): the hub becomes one main web server for every project, later with authentication; cross-project services (the arXiv feed that recommends new works) live in it; a second pilot in a different domain tests the tools and the human gates; then the factory goes deeper (data integration, graphs, hypotheses). Builds on: the site hub (IDEA-54, 55; `services/site*.py`), the discovery feed (IDEA-58, decision 118, 119), IDEA-04 (cross-project), decision 112.

## 1. What exists

- The hub server (`services/site_server.py`) is bound to one `Project`: one folder `<project>/site/`, one `Rebuilder`, one write lock, one per-start token, loopback only, seven allow-listed POST acts that run as the local human.
- The hub shell (`site.render_hub`) is one page per project with a product list from `site.products()`.
- The discovery feed (`services/feed.py`) fetches new arXiv listings by category and ranks them against a project's core works. The fetch cache is shared across projects; configuration, entries and reactions are per project. It has not been run live. The learned preference ranker is not built.
- Projects are folders under `data/projects/<slug>/` (`FACTORY_ROOT`), today one (`agentic-science`).

## 2. Parts

1. **Main server.** One process serves `/` (a portal listing every project under the root: title, event count, staleness, last activity, miners and queue state read from each project's own events) and each project at `/p/<slug>/` with its built `site/` folder. The per-project pieces (Rebuilder, write lock, advance gate, resume runner) are created per project on first use. The token and the loopback check stay shared at first. Every act names its project in the path (`/p/<slug>/api/...`); the actor is still the local human.
2. **Authentication seam.** A single function decides who a request is (today: loopback, the local human). Later an authenticator can replace it and map a user to the projects they may open; the acts already authorise by command row, so a project permission is a second check, not a rewrite. No login screen now.
3. **Shared feed.** The arXiv daily listing is fetched once per category set (the shared cache). The portal's "New publications" page ranks the listing against each project's reference works and shows, per project, the top picks with a one-click add to that project's queue; reactions stay per project. Unchanged rules: a ranking orders and judges nothing, held-out seeds are never shown, the platform calls no model.
4. **Project lifecycle in the portal (read-only first).** Create, archive and clean-up stay CLI acts at first; the portal shows each project's state and links to its own pages.
5. **Clean-up before pilot 2.** One decision list: the stale old root (read-only), the worktrees and branches of merged work (`mine-status-perf`, `miner-agreement-rate`, `idea-66-67`, `lifecycle-hub`), the old agent worktree `agent-a003be8dac716d1e7` (branch `plan-teams-a`, 26 unlanded commits: a decision, not a delete), the scratchpad, the main checkout still on `plan-2d-extraction`.
6. **Pilot 2 (different domain, pilot scale).** A clean project run step by step with the human gates of pilot 1: question, seeds, probe, protocol, calibration, rulings. Topic from the researcher (given later). What is tested is whether each gate stops and asks: every step that needs a ruling must refuse to go on without it, and every agent-written event carries its provenance. A gate that is skipped is a defect to record, not to patch around in the pilot.
7. **Deeper factory (after the hub).** Data integration across miners (one table of works with every miner's typed values), the graph (lineage, relations, citations: `graph_export`, `graph_query` exist and have not been run on the pilot), and the hypotheses engine (`hypothesis_*`, `experiment_design`, `region_*` exist and have not been run on a real corpus). First step: run each on `agentic-science` and record what works, what fails and what the researcher needs from it.

## 4. Risks

- **One process, many projects.** A long rebuild of one project must not block the others (one rebuild thread per project, one build at a time per project). A write to project A never takes project B's lock.
- **Paths.** Every link in the built pages is relative to the project's `site/` folder today; under `/p/<slug>/` they must still resolve (the explorer link `../explorer/index.html#open=<slug>` does). A test builds two projects and follows each link.
- **Token and origin.** The token is per start and per server; with several projects a token for one must not authorise an act on another: the path's slug is part of what is checked.
- **Feed shows works held out in a project.** The feed already refuses held-out seeds per project; the portal must apply the project's own rule per card.
- **Scope.** This is a refactor of a 593-line server and a 934-line hub shell; it needs a review round and a live check in a browser.
