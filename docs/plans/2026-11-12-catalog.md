# Plan: capability catalog — the factory's tools and skills, by lifecycle stage

Date: 2026-11-12 · Status: draft, under the researcher's review · Branch: `plan-catalog` off
`plan-feed-hub` · Backlog: IDEA-55 (one roof; the catalog moves to the factory hub when it exists)

## Goal

The researcher can see what the factory can do at each stage of the research-development lifecycle:
which skill to use when, which tools it calls, and the steps that call them. The page also flags
skill instructions that contradict the code, the decision log or each other.

Audience: the researcher, not the agent or the maintainer. Plain words come first; schemas are
behind a disclosure.

## Scope

In: one project-hub product `catalog`, built by `factory site build --only catalog`; a `stage:`
frontmatter field in every `plugin/skills/rf-*/SKILL.md`; mechanical instruction flags.
Out: the factory hub; MCP prompts (none are registered); example files (none exist); any
judgement of whether a flagged clash is real (scripts never judge).

The list is layout. Which stage a skill belongs to is data in its SKILL.md; which stage a tool
belongs to is derived.

## Derivation (nothing on the page is typed by hand except labels and layout)

| Field | Source |
| --- | --- |
| Tool name, description, input schema | the built server's tool list (`build_server(...)`, then list tools), not source parsing |
| Tool registration count | AST count of `@server.tool()` in `mcp/server.py`, compared with the built list |
| Skill name, "when to use" (the *prompt*) | SKILL.md frontmatter `name`, `description` |
| Skill stage | SKILL.md frontmatter `stage` |
| Tool stage | primary stage of the skills that name it in backticks; primary = earliest in lifecycle order |
| *Examples* | each numbered procedure step in a SKILL.md that names a tool, shown under that tool with its skill |
| Decisions cited | `decision N` references in SKILL.md, checked against `docs/decisions.md` headings and status |

Each tool appears exactly once, under its primary stage; the other stages that use it are shown
as "also used in" links. A tool no skill names goes to **Unassigned**.

## Page

1. Header: counts (tools registered / listed, skills, prompts, examples, flags) and the count
   check. A mismatch is a red banner naming the missing or duplicate tools.
2. One section per stage, in lifecycle order: skill cards ("when to use", steps that call tools),
   then that stage's tools (description; inputs behind a disclosure; examples; "also used in").
3. Unassigned tools.
4. Flags table (below), each with the file and line it comes from.
5. Footer: build time, code hash, skill file hashes.

## Flags (mechanical; shown for the researcher to judge)

| Code | Rule |
| --- | --- |
| `skill-unknown-tool` | a SKILL.md names, in backticks with a tool-shaped name (`[a-z]+(_[a-z]+)+`) next to "call"/"use", a tool that is not registered |
| `skill-unknown-arg` | a SKILL.md writes `tool(arg=…)` or "`tool` with `arg`" where `arg` is not in the tool's input schema |
| `skill-skill-clash` | two skills name the same tool in sentences of opposite polarity (one with never / do not / must not, the other with always / must / call) |
| `skill-decision-missing` | a cited decision number has no heading in `docs/decisions.md` |
| `skill-decision-not-decided` | a cited decision exists but is not marked *Decided* |
| `orphan-tool` | a registered tool that no skill names |
| `orphan-skill` | a skill that names no registered tool |
| `skill-no-stage` | a SKILL.md without `stage`, or with a value outside the lifecycle |

The platform never rules on a clash; it lists both sentences side by side.

## Build and staleness

- `Product(id="catalog", group=<factory group>, inputs=(), ...)`: the catalog reads no events.
- The fingerprint must change when a SKILL.md or `decisions.md` changes, not only with the code
  hash: add their hashes to the catalog's fingerprint (or make `code_hash` cover `plugin/skills`).
- A failure in the catalog build is isolated by the registry; other products still build.

## Acceptance

- The page builds with `factory site build --only catalog` on a copy of a project, and a failed
  build does not stop the other products.
- Every tool registered in `mcp/server.py` appears exactly once. The count check is part of the
  build, and a mismatch is shown on the page.
- Nothing on the page is typed by hand except labels and layout.
- `ruff` and `mypy --strict` pass.
